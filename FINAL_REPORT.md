# Final Report — Car Rental System

## Загальний опис
Car Rental System — консольний застосунок для управління орендою автомобілів,
розроблений протягом 4 ітерацій (Lab 34-37) як навчальний капстоун з ООП.

## Архітектурні рішення

### Чистий поділ на шари
Проєкт розділений на 4 шари з однонаправленими залежностями.
Domain не залежить ні від чого — це дозволило писати юніт-тести
без жодних моків чи підготовки інфраструктури.

### Repository патерн
Інтерфейси репозиторіїв в Domain дозволили мати дві реалізації:
InMemory для тестів і JSON для продакшну. RentalService не знає
яка реалізація використовується — це класичний DIP.

### Strategy патерн
Тарифи реалізував через IPricingStrategy. Додавання нового тарифу
не вимагає зміни RentalService — достатньо нового класу і реєстрації
в Program.cs. Це пряма демонстрація OCP.

### Command патерн
Кожну дію меню виніс в окремий клас що реалізує ICommand. AppRunner
не знає про конкретні команди — працює через інтерфейс.
Program.cs збирає все разом — єдина точка конфігурації.

## Що було складним

### JSON persistence з відновленням стану
Найскладніша частина — коректне відновлення стану авто після
завантаження з файлу. При десеріалізації оренди конструктор Rental
перевіряє чи авто доступне, але під час завантаження авто ще не має
правильного стану. Вирішив це через тимчасовий MakeAvailable() перед
створенням об'єкта з подальшим встановленням правильного стану.

### Рефакторинг Program.cs
Початковий Program.cs мав 200 рядків з великим switch. Після рефакторингу
до Command патерну скоротив його до 46 рядків і зробив розширення
тривіальним — новий пункт меню це новий клас, не зміна існуючого коду.

## Що залишилось поза scope
- Валідація формату email і телефону
- Обмеження кількості активних оренд на клієнта
- Логування помилок у файл
- Графічний або веб інтерфейс
- База даних замість JSON

## Продуктивність структур даних

### Dictionary для стратегій
`Dictionary<string, IPricingStrategy>` забезпечує O(1) пошук стратегії
за назвою. При виборі тарифу під час оренди — миттєвий доступ
незалежно від кількості зареєстрованих стратегій.

### List для репозиторіїв
`List<Car>` з LINQ-фільтрацією — O(n) для пошуку. Для навчального
проєкту з десятками записів це оптимально. При масштабуванні
до тисяч записів варто замінити на Dictionary або індекс.

## Покриття SOLID
- **S** — RentalService не серіалізує, JsonRepository не містить логіки
- **O** — нові тарифи і команди без зміни існуючого коду
- **L** — JsonRepository повністю замінює InMemoryRepository
- **I** — окремі інтерфейси для Car, Client, Rental репозиторіїв
- **D** — RentalService залежить від інтерфейсів, не від класів

## Висновок
Проєкт демонструє інтеграцію основних тем курсу ООП на реальному
бізнес-сценарії. Архітектура витримала 4 ітерації змін без переписування
існуючого коду — що і є головним доказом якості дизайну.
