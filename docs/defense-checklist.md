# Defense Checklist

## Головний сценарій демонстрації
1. Запустити програму
2. Показати авто відсортовані за ціною
3. Орендувати Toyota Camry на 5 днів зі знижкою 10% → 3600 грн
4. Показати активні оренди
5. Повернути авто
6. Показати аналітику — дохід 3600 грн

## Негативний сценарій
1. Спробувати орендувати авто що вже зайняте
2. Показати що воно зникло зі списку доступних
3. Вийти і перезапустити — показати що стан відновився

## 5 питань про архітектуру
**1. Де видно SRP?**
RentalService містить тільки бізнес-логіку. JsonCarRepository тільки серіалізує.
AppRunner тільки керує меню. Кожен клас має одну причину змінюватись.

**2. Де видно OCP?**
Новий тариф — новий клас що реалізує IPricingStrategy, нічого не міняю в RentalService.
Нова команда меню — новий клас ICommand, нічого не міняю в AppRunner.

**3. Де видно DIP?**
RentalService отримує ICarRepository в конструкторі. У тестах підставляю
InMemoryCarRepository, у продакшні JsonCarRepository. Сервіс не знає різниці.

**4. Чому Dictionary для стратегій?**
O(1) пошук за назвою. При виборі тарифу під час оренди — миттєвий доступ
незалежно від кількості стратегій. List давав би O(n).

**5. Чому Command патерн замість switch?**
Switch на 200 рядків — важко розширювати і читати. Command патерн — кожна
дія окремий клас, новий пункт меню це новий файл без зміни AppRunner.

## 5 питань про тестування
**1. Який тест дає найбільшу впевненість?**
`SaveAndReload_Rental_PreservesStatus` — перевіряє повний цикл: оренда,
збереження, завантаження, перевірка статусу. Якщо він проходить — persistence працює.

**2. Чому 42 юніт і 8 інтеграційних?**
Юніт-тести швидкі і ізольовані — перевіряють логіку без файлів.
Інтеграційні перевіряють що компоненти працюють разом. Це test pyramid.

**3. Навіщо Theory тести?**
Один тест з кількома наборами даних замість кількох однакових тестів.
Перевіряю граничні значення: ціна 700, 800, 1500 — різні результати.

**4. Як тестуєш JSON без реальних файлів?**
Використовую `Path.GetTempPath()` — тимчасова папка що видаляється в Dispose().
Тест не залежить від файлів на диску.

**5. Чому AppRunner не покритий тестами?**
Залежить від Console.ReadLine() — важко тестувати без додаткових абстракцій.
Це зафіксований технічний борг в iteration-3.md.

## 3 питання про компроміси

**1. Чому JSON а не база даних?**
Для навчального проєкту JSON достатньо і простіше. При масштабуванні
замінив би JsonRepository на SqlRepository не змінюючи RentalService — завдяки DIP.

**2. Що б змінив якби починав заново?**
Виніс би Console.ReadLine() за інтерфейс IConsole щоб команди можна було тестувати.
Також додав би валідацію email і телефону в доменних класах.

**3. Які ризики залишились перед релізом?**
Немає валідації формату даних, немає обмеження активних оренд на клієнта,
AppRunner не покритий тестами. Все зафіксовано в iteration-3.md і release-plan.md.
